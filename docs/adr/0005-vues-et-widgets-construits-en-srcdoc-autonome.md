# L'Hôte construit chaque Vue et chaque Widget en document `srcdoc` autonome

Les fichiers d'un Module n'existent que dans le navigateur de l'Utilisateur (ADR 0002), et chaque Vue ou Widget doit tourner dans une iframe sandbox d'origine opaque (ADR 0001) dont l'Hôte **bloque** les accès réseau non déclarés (ADR 0004). Aucun serveur ne peut donc servir ces fichiers, et aucun service worker non plus : les navigateurs ne font passer par un service worker ni la navigation d'une iframe sandbox sans `allow-same-origin`, ni les requêtes d'un document d'origine opaque. L'Hôte construit donc lui-même le document de l'iframe (`<iframe sandbox srcdoc>`). La politique de sécurité de contenu (CSP) dérivée des Permissions y est placée en `<meta>` avant tout contenu du Module, les fichiers locaux référencés y sont intégrés en URL `data:`, et un petit runtime injecté sert le reste : `fetch` et `XMLHttpRequest` relatifs, URL relatives posées à l'exécution, Web Workers, et imports ES via une import map.

Mesures du prototype (branche `prototype/01-iframe-sandbox`, `prototypes/01-iframe-sandbox/`), sur Chromium 143, Chrome 155, Firefox 144 (Gecko de Playwright) et WebKit 26 (Playwright), puis à la main dans Safari 26.6.2 (macOS 26.6.2) pour l'approche retenue :

- avec cette approche, et les fichiers relus depuis IndexedDB, la page, sa feuille de style, ses images, ses scripts classiques et ES modules (avec import relatif), un Web Worker et un `fetch` relatif se chargent dans les quatre navigateurs et dans Safari, sans qu'aucune requête vers les fichiers du Module ne parte sur le réseau. Une requête et une image vers l'origine déclarée réussissent ; vers une origine non déclarée, elles sont bloquées par le navigateur avant d'atteindre le serveur ;
- un Web Worker démarré depuis un fichier local hérite de la CSP : sa requête vers l'origine déclarée réussit, celle vers une origine non déclarée n'atteint jamais le serveur (Firefox la signale comme violation de CSP) ;
- le Module tourne en origine `null` et n'a pas accès à IndexedDB.

## Considered Options

- **Service worker de l'Hôte** servant `/m/<id>/…` avec un en-tête CSP : rejeté. Avec l'attribut `sandbox`, la navigation de l'iframe n'atteint pas le service worker (dans les quatre navigateurs, elle part sur le réseau). Si l'on remplace l'attribut par une directive CSP `sandbox` dans la réponse, la navigation est bien interceptée, mais le document devient opaque et ses ressources relatives ne sont plus servies : elles partent sur le réseau (Chromium, Chrome, WebKit) ou ne se chargent pas du tout (Firefox). Cette variante a un défaut de plus : sans service worker actif (premier chargement, rechargement forcé), l'iframe chargerait sans sandbox une page de l'origine de l'Hôte.
- **Origine dédiée au contenu des Modules**, avec iframe sandbox sans `allow-same-origin` : rejetée pour la même raison, car un document opaque n'est jamais contrôlé par un service worker, quelle que soit son origine.
- **Origine dédiée avec `allow-same-origin`** : c'est la seule variante « serveur » qui fonctionne, dans Chromium, Chrome et WebKit (dans le Firefox de Playwright, le Module ne démarre pas). Elle est rejetée, car le Module devient même-origine que la mécanique qui le sert. Il pourrait réécrire ses propres fichiers et sa CSP stockés, désinscrire le service worker, ou lire le stockage et les fichiers des autres Modules s'ils partagent l'origine. Une origine par Module (sous-domaines génériques) exigerait des sous-domaines wildcard, non pris en charge par Cloudflare Pages, donc un Worker dont le coût croît avec l'usage, sans régler la falsification de la CSP. Elle contredit aussi la Convention (§4, origine opaque).
- **`srcdoc` sans intégration**, avec CSP en `<meta>` et `<base>` vers `/m/<id>/` : rejeté, car les ressources relatives partent sur le réseau, faute de service worker.

## Consequences

- **Hébergement Cloudflare Pages** : un seul domaine, aucun Worker, aucune fonction ni sous-domaine supplémentaire. Le coût reste celui d'un site statique, donc nul. Seul l'en-tête `Content-Security-Policy: frame-src 'none'` est nécessaire sur les pages de l'Hôte (`_headers`). Vérifié dans les trois moteurs et dans Safari : il n'empêche pas les iframes `srcdoc`, et il bloque la navigation d'une Vue vers une origine non déclarée (`location.href = …`), qui fuit sans lui.
- Un document `srcdoc` **hérite de la CSP de l'Hôte**, qui se combine à la sienne. L'Hôte ne doit donc pas restreindre pour lui-même les directives de chargement (`script-src`, `connect-src`, `img-src`…), sous peine de casser les Modules. Sa propre protection repose sur l'absence de contenu non fiable dans son origine. Avec `frame-src 'none'`, un Module ne peut intégrer aucune iframe, même vers une origine déclarée. Comme cela s'écartait de la Convention §4 (« remote resources from the origins declared in its Permissions »), la Convention est précisée en révision mineure. Les ressources distantes sont énumérées (scripts, styles, images, polices, médias). Un Module ne peut ni intégrer de frame, même vers une origine déclarée, ni naviguer son iframe vers une autre URL, y compris une autre page de son paquet. Chaque Vue et chaque Widget est donc une page unique, où seul un routage par `location.hash` fonctionne : `history.pushState` avec une URL lève une `SecurityError` (vérifié dans les trois moteurs). Le Validateur signale une frame intégrée (`sandbox/unavailable-api`).
- La CSP d'une Vue ou d'un Widget ne liste aucune URL de l'Hôte : `default-src <origines déclarées> data: blob: 'unsafe-inline' 'unsafe-eval'`, `form-action <origines déclarées ou 'none'>`, `base-uri` limité à la base injectée. Une ressource locale que le runtime n'a pas réécrite est bloquée par la CSP au lieu de partir sur le réseau.
- **Fuites résiduelles** (statut mesuré) :
  - nouvel onglet (`allow-popups-to-escape-sandbox`, requis par la Convention §4) : **fuite** confirmée dans les quatre navigateurs sous Playwright, car l'URL ouverte peut porter des données. Ce test n'a pas été fait dans Safari, dont le bloqueur arrête une ouverture qui ne vient pas d'un clic ; un clic de l'Utilisateur dans le Module suffirait à la permettre ;
  - WebRTC : **fuite** confirmée dans Chromium, Chrome, WebKit et Safari (paquets STUN vers un serveur non déclaré) ; non vérifiable dans le Firefox de Playwright, qui n'émet aucun paquet STUN même depuis la page de l'Hôte hors sandbox (témoin mesuré). Aucun navigateur n'applique de directive CSP pour WebRTC, et supprimer `RTCPeerConnection` côté runtime se contourne ;
  - navigation de l'iframe elle-même : bloquée par `frame-src 'none'` de l'Hôte ;
  - formulaire (avec `allow-forms`, requis par la Convention §4) et `<link rel=prefetch>` vers une origine non déclarée : bloqués par la CSP (`form-action`, `default-src`), y compris dans Safari.
- Le runtime est une couche de compatibilité, pas une frontière de sécurité. Un Module qui le contourne obtient au pire une ressource locale introuvable, jamais un accès réseau non déclaré, puisque seule la CSP fait autorité.
- Dans Firefox, une feuille de style `<link>` intégrée en `data:` s'applique parfois une dizaine de millisecondes après l'événement `load` (mesuré : 3 exécutions sur 4). Un Module qui lit ses styles calculés dès le chargement peut donc voir un état non stylé.
- Le document embarque les fichiers en base64 (+33 %) pour chaque Vue et chaque Widget ouverts, avec un paquet limité à 10 Mo.
